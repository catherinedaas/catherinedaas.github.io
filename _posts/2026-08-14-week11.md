Week 11, August 10 - August 14

This week had the flashiest output! We are still working on getting the metric norms part of the file ready for presentation to clinical partners, but this week was video and IMU processing! So there were a few challenges to overcome. Primarily, none of the original videos or trials were done with video syncing and pose estimation as a goal. Also, some of the information that might be useful is controlled by other processes. The anchor for the IMU data to wall clock time gets designated by the app that runs the trials. The app code is not in the repo that has been the basis for the student portion of the project. 

We decided on a pilot trial for the pose estimation project to use three video cameras to get alternate views of the board and subject. One of these video angles was chosen to match the hard to work with oblique video angle used in some of the trials. We used two androids and an iOS device. The videos need to be synced to each other and the IMU data in a compelling and easy to verify method. This last is a real trick, because I am a student transitioning into coding. The code underlying the pose estimation portion of this project has been done in a podman container using two bind mounts, one with RW permissions and one with RO permissions. This allows for easy extraction of developed code from the container but enforces safety for the data, in the RO directory. Specifically, the data is IMU data from the board during the pilot trial for this project and video of me, an individual student with no HIPAA concerns. The internet access on the container is set up to be outbound only to allow for pip install and various libraries needed for the project. Inbound access is severely curtailed to protect my PC. The whole thing is backed up by git inside the container with no shared repo access. This is a little disconcerting as there is no cloud backup as of yet. This will probably be managed next week.  

My first challenge was syncing the phone videos. They all have datetimes but lining those up with each other isn't enough to sync videos with variable padding at their start. The pixel datetime was stamped at file close and the iPhone stamp happened at file open. The trials start almost 2 minutes into the longest video. Still this could be simple math, except looking at timestamps is not enough to sync between the 28min video and the various 30s IMU trials time stamps. It just didn't work lining up on timestamps for anything. 

To solve some of these problems a small Python module was written to read the video containers directly. It works out each recording's start time, length and codec, and the other four scripts import it so they all agree on where a file sits in the session. There are some logic gates for determining where in the video the timestamp comes from. The pixel preserves the milliseconds associated with its real start time in its file name. The iPhone's had to be determined by using the file's duration, modification time, and creation time. It was important to be able to handle videos from multiple devices because this is being developed for downstream use with a variety of cameras. 

These time stamps still left almost a second of mismatch so the audio waveform was used to improve the syncing. This was done by comparing the audio/pressure measurements in 27 blocks of 20 seconds spread across the whole session. This is used to fit the wave forms, and thus the videos, together across the three cameras for syncing. Timestamps alone left two cameras 55 frames apart. Measuring from the room sound instead brought that inside three frames.

Like I mentioned before, I am new to coding. While I did have experience with matplotlib and library calls and stats before this summer, I had never done anything with video files. The video syncing was a great example of how Claude code can speed things up. I can do a lot of different experimental methods to solve these problems and visualize which is the most successful before choosing one to move forward. I can look at video very easily and judge if that video is synced. Claude was able to use the audio waveforms to very swiftly improve upon what I was able to achieve on my own with time stamps and it became obvious that the audio data was going to be very useful. 

The checks on all of this were to create a small web app to visualize outcomes. For example, all three videos playing side by side, with distinctive movements correctly timed and mirrored were how success was confirmed. Similarly, strip charts of the audio waveform and the IMU data were used to better track when events like sounds from the board and rapid changes in board pitch and roll were measured. Finally, a visualization projected over the board showing the pitch or roll (depending on camera angle), were also used to confirm good syncing of the IMU data and the videos. 

The actual syncing of the IMU data to the videos was the most challenging. When timestamps from the IMU data were lined up with the videos everything was confusing and unsynced. It was terrible. It turns out the timestamp for each trial is written around 1.9s after the trial ends. That delay varied by about a third of a second from trial to trial, with no drift across the session. So it is currently thought that the 1.9s represents the app's write latency and the write time was initiated around 30s after the start of the trial. Unfortunately, that means no single correction can be used to place the start of any one trial. Every trial has to be measured, in every session.

This was determined using two independent methods. Both methods agreed on how much the delay changed from trial to trial, to within a tenth of a second. Three trials contained beeps whose exact firing times the board had already recorded, so finding those beeps in the audio gave the error directly. The second method was the web app whose output was the offset time in seconds. All of the data was lined up by eye and could be adjusted frame by frame. Matching on these three trials was then extrapolated and used to aid with the manual fit of IMU data. Generally, the IMU data was placed around a -31s offset and then manually adjusted for best fit. This general fit continued to match for the other manually checked trials that did not have buzzers available to check against.
